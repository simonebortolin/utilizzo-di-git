\section{Le 5 W}

\begin{frame}{Cos'è Git}
    \begin{itemize}
        \item Git è un software di controllo della versione centralizzato, chiamato anche (VCS - Version Control System).
        \item Permette di tenere traccia delle modifiche apportate ai file di un progetto nel tempo.
        \item È stato creato da Linus Torvalds nel 2005 per gestire lo sviluppo del kernel Linux.
    \end{itemize}
\end{frame}
\begin{frame}{Cosa fa Git}
    \begin{itemize}
        \item Git si occupa di archiviare la cronologia delle modifiche al progetto.
        \item Vengono registrate tutte le modifiche, si può tornare indietro e si può confrontare il codice.
        \item Quando vengono fatte delle modifiche al progetto le modifiche esse rimangono in locale e non vengono direttamente sincronizzate in realtime ma bisogna effettuare un \textbf{commit} e questo commit contiene una descrizione sintetica delle modifiche, oltre che alle informazioni sull'autore della modifica.
        \item Ogni  \textbf{commit} rappresenta uno stato del progetto in un determinato momento.
        \item Un \textbf{commit} rappresenta l'unità minima logica di un cambiamento.
        \item I commit sono organizzati in una storia (o log) dei cambiamenti.
        \item Git permette di gestire più rami di sviluppo per esempio per gestire feature diverse o team di sviluppo separati. 
        \item Git utilizza un sistema di branching e merging per gestire le diverse linee di sviluppo.
        \item Git ti permette di scoprire di ha effettuato delle modifiche e perché.
    \end{itemize}
\end{frame}
\begin{frame}{Quando si usa Git}
    \begin{itemize}
        \item Git si utilizza su un \textbf{progetto}, cioè il codice per una app o un software o un suo componente, possiamo individuare un progetto come una struttura di cartelle o "albero dei file".
        \item Uno sviluppatore del team potrebbe lavorare su una nuova funzionalità del progetto mentre un altro sviluppatore corregge un bug non correlato modificando il codice, ogni sviluppatore può apportare le proprie modifiche in diverse parti dell'albero dei file.
        \item Il controllo della versione aiuta i team a risolvere questo tipo di problemi, aumentando le capacità di sviluppo contemporaneo e simultaneo, riducendo i conflitti e avendo uno storico delle modifiche.
    \end{itemize}
\end{frame}
\begin{frame}{Dove si usa Git}
    \begin{itemize}
        \item Git si utilizza su qualsiasi computer o telefono, su qualsiasi tipo di file, anche se Git preferisce i file di testo, su qualsiasi dimensione di progetto
        \item Non vi sono particolari limiti all'utilizzo.
        \item Git si utilizza quando è necessario condividere il codice con altri device o altre persone in quanto è molto facile condividere facilmente il codice con altre persone.
        \item Sebbene sia possibile sviluppare software senza utilizzare alcun controllo di versione, ciò comporta un enorme rischio per il progetto che nessun team di professionisti dovrebbe accettare. Quindi la domanda non è se usare il controllo versione ma quale sistema di controllo versione usare (VCS).
    \end{itemize}
\end{frame}
\begin{frame}{Perché si usa Git}
    \begin{itemize}
        \item Git ti permette di ripristinare file alle versione precedenti per rimuovere modifiche errate o non volute
        \item Git ti permette di vedere la cronologia delle modifiche ai file e quindi raccoglie le conoscenze del team sullo sviluppo, magari è stata modificata una funzione perché ha un bug, ma data la memoria corta viene rifatto il codice uguale a prima, dimenticandosi dell'altro bug.
        \item Il controllo della versione protegge il codice sorgente sia dalla catastrofe sia dal degrado casuale dell'errore umano e delle conseguenze indesiderate.
        \item Gli sviluppatori di software che lavorano in team scrivono continuamente nuovo codice sorgente e modificano il codice sorgente esistente: magari il codice non è perfettamente aggiornato o dopo una semplice modifica tutti gli sviluppatori non riescono più a compilare.
        \item Git ti permette di effettuare operazioni \textbf{merge} tra i vari rami del progetto segnalando e gestendo eventuali \textbf{conflitti}.
    \end{itemize}
\end{frame}

\begin{frame}{Best practice}
    \begin{description}
        \item[Fare spesso commit] I commit sono facili e veloci. Dovrebbero essere eseguiti frequentemente per acquisire gli aggiornamenti di una base di codice. Ogni commit è un'istantanea su cui è possibile ripristinare la base di codice se necessario. I commit frequenti offrono molte opportunità di ripristinare o annullare il lavoro. Un gruppo di commit può essere combinato in un singolo commit usando un rebase per chiarire il registro di sviluppo. 
        \item[Programma sempre sulla versione corretta] i VCS permettono aggiornamenti rapidi da più sviluppatori. È facile avere una copia locale non sincronizzata, rendendo più difficile il merge!
        \item[Dettaglia bene le modifiche] Ogni commit ha una voce di registro corrispondente. Al momento della creazione del commit, questa voce di registro viene popolata con un messaggio. È importante lasciare messaggi di registro di commit esplicativi descrittivi. 
    \end{description}
\end{frame}
\begin{frame}{Best practice}
    \begin{description}
        \item[Usa i rami] Il ramo è un potente meccanismo del VCS che consente agli sviluppatori di creare una linea di sviluppo separata. I rami dovrebbero essere usati frequentemente in quanto sono rapidi ed economici. 
        \item[Concorda un metodo unico per la gestione del flusso] Si decide una linea guida per fare le fusioni, per la creazione di rami e tutto!
        \item[Evita di abusare delle feature di Git] Evita di fare troppi commit, i commit rappresentano l'unità minima logica di un cambiamento, non farne né troppi né troppo pochi.
    \end{description}
\end{frame}

\section{Architettura di Git}

\begin{frame}{Design di Git}
    Il design di Git è stato basato su 5 punti:
    \begin{itemize}
        \item Velocità
        \item Semplicità di design e uso
        \item Supporto per sviluppo non lineare (migliaia di versioni parallele)
        \item Completamente distribuito
        \item Abilità di gestire grandi progetti
    \end{itemize}
    
    La differenza principale tra Git e altri VCS sta in come Git pensa e
    vede i propri dati.
    
    \begin{itemize}
        \item Molti VCS (come CVS e Subversion) vedono i dati che gestiscono come un set di file e di cambiamenti apportati a tali file nel tempo (delta-based version control)
        \item Git vede i dati come una serie di snapshot di un filesystem in miniatura.
    \end{itemize}
\end{frame}
\begin{frame}{Gli oggetti di Git}
    Git è basato principalmente su due strutture dati:
    \begin{itemize}
        \item Un \textbf{indice mutabile} (chiamato stage o cache) nel quale vengono raccolte tutte le informazioni sulla directory di lavoro
        \item Un \textbf{object database immutabile} che può contenere 4 tipi di oggetti (blob, tree, commit, tag), queste strutture possono essere viste come dei \textbf{puntatori}.
    \end{itemize}    
\end{frame}

\section{Storia di Git e differenze con altri DVCS}

\begin{frame}{Storia di Git}
    Git è nato nel  2005,  per gestire il codice sorgente del kernel di Linux;

    Scritto da Linus Torvalds, che voleva un sistema distribuito che si potesse usare come BitKeeper, ma nessuno dei sistemi disponibili gratuitamente soddisfaceva i suoi bisogni, particolarmente il suo bisogno di velocità. BitKeeper non lo poteva più usare gratuitamente in quanto Andrew Tridgell aveva effettuato il reverse engineering dei protocolli.
    
    È un sistema di version control distribuito, pensato per gestire grandi cartelle di codice sorgente ma con la possibilità di gestire qualsiasi tipo di file.
\end{frame}
\begin{frame}{Il nome Git}
    Cosa può significare Git?
    \begin{enumerate}
        \item 3 lettere casuali mai usate dagli OS UNIX quindi utilizzabili.
        \item nello slang americano significa idiota/stupido
        \item Global Information Tracker ma solo quando sei bravo (monitoraggio delle informazioni globali)
        \item Goddamn Idiotic Truckload (dannato carico di camion idiota) ma solo quando non funziona
    \end{enumerate}
    Linus affermò che ha scelto Git propio perché nello slang americano significa idiota/stupido e gli sembrava divertente.
\end{frame}

\begin{frame}{Come scegliere un VCS}
    Cosa deve avere un VCS perché sia valido?
    \begin{enumerate}
        \item \textbf{Una cronologia completa delle modifiche a lungo termine di ogni file.} Deve poter memorizzare tutti i cambiamenti apportati da molte persone nel corso degli anni. Le modifiche includono la creazione e la cancellazione di file, nonché modifiche al loro contenuto. Questa cronologia dovrebbe includere anche l'autore, la data e le note scritte sullo scopo di ogni modifica. Avere la cronologia completa consente di tornare alle versioni precedenti per aiutare nell'analisi della causa principale dei bug ed è fondamentale quando è necessario risolvere i problemi nelle versioni precedenti del software. Se il software viene lavorato attivamente, quasi tutto può essere considerato una "versione precedente" del software.
        \item \textbf{Ramificazione e fusione.} La creazione di rami permette di far lavorare i membri del team contemporaneamente senza infastidirsi a vicenda, ed ogni volta che i vari pezzi di codice sono stati completati si "fondono" insieme, e far si che chi fonde sia in grado di gestire solamente i veri conflitti, evitando di dover controllare tutti i file anche per minuscole differenza
    \end{enumerate}
\end{frame}
\begin{frame}{Come scegliere un VCS}
    \begin{enumerate}\setcounter{enumi}{3}
        \item \textbf{Tracciabilità.} Essere in grado di tracciare ogni modifica apportata al software e essere in grado di annotare ogni modifica con un messaggio che descrive lo scopo e l'intento della modifica può aiutare l'analisi della causa principale del bug. Avere la cronologia annotata del codice a portata di mano quando si legge il codice, cercando di capire cosa sta facendo e perché è così progettato può consentire agli sviluppatori di apportare modifiche corrette e armoniose in accordo con il progetto a lungo termine previsto del sistema. Ciò può essere particolarmente importante per lavorare in modo efficace con il codice legacy ed è cruciale per consentire agli sviluppatori di stimare il lavoro futuro con precisione.      
    \end{enumerate}
\end{frame}

\section{Installazione di Git}

\begin{frame}[fragile]{Installazione di Git su Linux}
    
    Per installare Git su un sistema operativo tipo Ubuntu, Debian, ...
    \begin{lstlisting}[language=bash]
$ sudo apt update
$ sudo apt install git\end{lstlisting}
    Dopo di che dal termianle verificare che l'installazione è andata a buon fine:
    \begin{lstlisting}[language=bash]
$ git --version\end{lstlisting}
    Impostiamo le nostre credenziali:
    \begin{lstlisting}[language=bash]
$ git config --global user.name "Emma Paris"
$ git config --global user.email "eparis@atlassian.com"\end{lstlisting}
    
    Consiglio di non usare credenziali che non conducano espressivamente alla persona che ha scritto il codice (furbissimo@gmail.com) in quanto queste credenziali restano salvate per sempre, come se fosse blockchain o la cronologia di Wikipedia
\end{frame}

\section{Uso distribuito di Git}

\begin{frame}{Repository remoto}
    Per consentire agli utenti di lavorare in maniera distribuita e di collaborare su un repository Git abbiamo bisogno del cosidetto repository remoto (detto anche remote), ovvero di una versione del nostro repository Git gestita e in hosting su Internet o su un'altra rete.

    Le operazioni di sincronizzazione con il remote sono tre: \textbf{fetch}, \textbf{pull} e \textbf{push}. Abbiamo già visto cosa fanno le operazioni di \textbf{pull} e \textbf{push} nella seconda slide DVCS.

    L'operazione di \textbf{fetch} invece è l'operazione precedente al \textbf{pull}, e scarica commit, file, e gli altri oggeti del database Git dal remote nella copia locale senza però l'\texttt{HEAD}.
    
\end{frame}
\begin{frame}{Remote URL}{HTTPS o SSH}
    Tutti i server Git (da GitHub a sourcehut passando per GitLab e Bitbucket) offrono la possibilità di avere un \textbf{remote url} del repository sia via SSH che via HTTPS
    \begin{description}
        \item[HTTPS] è il metodo più veloce, è ideale per scaricare i repository pubblici (solo operazioni di pull, non è sicuro per il push).
        \item[SSH] è il metodo più sicuro, è ideale per i repository in cui si contribuisce (operazioni di pull e push).
    \end{description}

    È possibile migrare i repository con un remote url da HTTPS a SSH in maniera molto semplice: basta rimuovere e riaggiungere il remote url.

\end{frame}
\begin{frame}[fragile]{Remote}{HTTP: Il problema del salvataggio delle credenziali offline}
    Se usiamo la riga di comando per fare push di un commit su un repository con un remote url HTTPS, ci chiederà ogni volta le credenziali del server. 
    \begin{block}{Password nei terminali unix-like}
        Attenzione, spesso quando si digita la password su terminali unix-like il terminale non da nessun feed per la digitazione delle password.
    \end{block}
    È possibile salvare le suddette credenziali tramite \lstinline{git config credential.helper store}. 
\end{frame}
\begin{frame}[fragile]{Remote}{HTTP: Il problema del salvataggio delle credenziali offline}
    \begin{alertblock}{Attenzione}
        L'uso di \texttt{git config credential.helper store} è altamente sconsigliato in quanto questo metodo salva le credenziali in un file di testo (plaintext) non cripato, che è il \lstinline{.gitconfig} globale, su linux si trova in \lstinline{/home/[username]/.gitconfig}. Per evitare questo comportamento è possibile:
        \begin{itemize}
            \item Impostare un timeout del file \lstinline{git config credential.helper cache <timeout>}, dove il timeout è scritto in secondi ed è opzionale con valore di default di 15 minuti, e quindi è necessaria reinserirla ogni 15 minuti.
            \item \textbf{Usare una chiave SSH e quindi non usare username e password}.
        \end{itemize}
    \end{alertblock}
\end{frame}
\begin{frame}[fragile]{Remote}{Chiave SSH}
    Per generare una chiave dobbiamo aprire il terminale, digitare \lstinline{ssh-keygen -t} seguito dal tipo di chiave (ed25519, RSA), scegliere il nome del file e la directory  (si può lasciare tutto di default).
    
    Infine specificare una  passphrase\footnote{\url{https://www.ssh.com/ssh/passphrase/}}, la passphrase se omessa potrebbe portare a problemi di sicurezza, è possibile rimuoverla o aggiungerla in un secondo momento la passphrase\footnote{\url{https://docs.github.com/en/github/authenticating-to-github/working-with-ssh-key-passphrases}}
    \begin{lstlisting}[language=bash]
$ ssh-keygen -t ed25519
Generating public/private ed25519 key pair.
Enter file in which to save the key (/home/[username]/.ssh/id_ed25519):\end{lstlisting}
    \Enter
\end{frame}

    \end{minipage}%

\begin{frame}[fragile]{Chiave SSH}
    Per condividere la chiave all'interno di Windows e WSL è necessario che la chiave sia presente sia su \lstinline{/mnt/c/Users/[username]/.ssh} che su \lstinline{~/.ssh}. Se si crea prima la chiave su WSL basta \footnote{\url{https://devblogs.microsoft.com/commandline/sharing-ssh-keys-between-windows-and-wsl-2/}}:

    Se si crea prima la chiave su Windows basta:

\begin{frame}[fragile]{IDE \& .gitignore}
    È importante sottolineare che nel repository .git non ci va per nessun motivo, ma per nessun motivo un file compilato, e neanche file di configurazione locali degli IDE e qualsiasi altra cosa che è legata al PC e non al progetto software (per esempio chiavi e password). Git mette a disposizione il file \texttt{.gitignore}, che è un file dove vengono specificati che file ignorare. Una collezzione di file \texttt{.gitignore} è presente su questo repository Git:
    \url{https://github.com/github/gitignore}
    
    In linea generale, consiglio di mettere i appendere i seguenti file gitignore in uno solo: Jetbrains, Visual Studio, Eclipse e quello del linguaggio di programmazione del repository (in questo caso C++)
    
    Dopo aver modificato il file \texttt{.gitignore}, nel caso in cui nel nostro repository ci siano file la cui presenza non è gradita, possiamo usare questo comando per "pulire" il repository:
    \begin{lstlisting}[language=bash]
$ git rm -r --cached . 
$ git add .
$ git commit -am "Remove ignored files"\end{lstlisting}

\begin{frame}{Branching}
    Con \textbf{operazione di branching}, in quasi tutti i VCS, si intende l'operazione tramite il quale l'utente "si stacca" dal principale ramo di sviluppo e continua a lavorare senza intaccare il ramo principale.
    In molti VCS viene vista come operazione dispendiosa di risorse e tempo, e raramente fa parte di workflow.
    
    In Git invece il branching è diventata una parte vitale del workflow di lavoro di molti utenti grazie alla semplicità nel creare nuovi branch e spostarsi tra di essi.

\begin{frame}[fragile]{Branching}
    Crea un nuovo branch chiamato \texttt{feature\_x} e passa al nuovo branch usando
    \begin{lstlisting}[language=bash]
$ git switch -c feature_x\end{lstlisting}
    Ritorna di nuovo su \texttt{main}
    \begin{lstlisting}[language=bash]
$ git switch main\end{lstlisting}
    E, solamente dopo un merge, cancella il branch creato in precedenza
    \begin{lstlisting}[language=bash]
$ git branch -d feature_x\end{lstlisting}
    
    Il branch non sarà disponibile agli altri fino a quando non verrà inviato al repository remoto
    \begin{lstlisting}[language=bash]
$ git push origin <branch>\end{lstlisting}
    Possiamo usare il comando \lstinline{git push -u origin <branch>} per dire a Git: salvami \texttt{origin <branch>}, così la prossima volta posso scrivere:
\begin{lstlisting}[language=bash]
$ git push\end{lstlisting}
\end{frame}

\begin{frame}[fragile]{Operazione di merge}{Scaricare ed unire le modifiche}
    Abbiamo visto che per aggiornare il tuo repository locale alla commit più recente si esegue
    \begin{lstlisting}[language=bash]
$ git pull\end{lstlisting}
    Nella tua directory corrente per aggiornare il repository locale alla versione remota, in background il \texttt{git pull} effettua un \texttt{git fetch} e per incorporare le modifiche fatte sul server remoto effettua un \texttt{git merge}.
    Il comando pull cerca di auto-incorporare le modifiche locali con la copia nel server, ma questo non sempre è possibile. 
\end{frame}
\begin{frame}{Operazione di merge}{Scaricare ed unire le modifiche}    
    Il caso appena descritto è il caso banale di merge: cioè quello in cui il commit presente nella working directory e nell'index è un antenato del commit con cui effettuaimo il merge, in questo caso si fa merge fast-forward. La referenza viene semplicemente spostata e viene eseguito il checkout sul nuovo commit.

\end{frame}
\begin{frame}[fragile]{Operazione di Merge}{Effettuare il merge}
    Quando si devono unire invece le modifiche di un branch in un altro branch è necessario effettuare un merge a 3 vie e non il fast-forward. Per incorporare nel branch della working directory un altro branch (ad esempio \texttt{new-feature}):
    \begin{lstlisting}[language=bash]
$ git merge <branch>\end{lstlisting}

    Ci sono varie strategie ma di default è Git usa il "merge ricorsivo" che prende il commit corrente (\texttt{ed489}), il commit del branch da unire (\texttt{33a04}), il loro antenato comune (\texttt{b325c}) ed esegue un merge a tre vie. Il risultato viene memorizzato nella working directory e nello stage, è verra fatto un commit con due genitori (\texttt{f8bc5}).

\end{frame}
\begin{frame}[fragile]{Operazione di Merge}{Conflitti}

    In entrambi i casi Git prova ad auto-incorporare le modifiche. Sfortunatamente, a volte questa procedura automatizzata non è possibile, ed in questo caso ci saranno dei conflitti.

here is some content not affected by the conflict
<<<<<<< main
this is conflicted text from main
=======
this is conflicted text from feature branch\end{lstlisting}

\begin{frame}[fragile]{Operazione di Merge}{Conflitti}
    In caso di file con conflitti Git mette in automatico i file nello stato "untracked".

    \begin{lstlisting}[language=bash]
$ git add <nomedelfile>\end{lstlisting}

    \begin{lstlisting}[language=bash]
$ git diff <branch_sorgente> <branch_target>\end{lstlisting}
    Infine si effettua il commit:
    \begin{lstlisting}[language=bash]

\begin{frame}[fragile]{Tags}
    È raccomandato creare dei tags nel caso in cui il software venga rilasciato. Questo è un concept già conosciuto, che esiste anche in SVN. Puoi creare un tag chiamato 1.0.0 eseguendo
    \begin{lstlisting}[language=bash]
$ git tag 1.0.0 1b2e1d63ff\end{lstlisting}
    la sequenza \texttt{1b2e1d63ff} rappresenta i primi 10 caratteri del commit che si vuol referenziale tramite questo tag. Puoi ottenere l'id della commit tramite.
    
    \begin{lstlisting}[language=bash]
$ git log\end{lstlisting}
    puoi anche utilizzare meno caratteri per l'id della commit, basta che sia unico.
\end{frame}
\begin{frame}[fragile]{Differenze apportate ai commit}
    Per Git, calcolare le modifiche apportate ai file da un commit all'altro non è poi difficile. Per esempio, puoi ricavarle con
    \begin{lstlisting}[language=bash]
$ git diff dev main\end{lstlisting}
    Con \lstinline{git diff from to} chiedi a Git «qual è l'elenco delle modifiche ai file che devo applicare a \texttt{from} perché il progetto diventi identico a quello fotografato in \texttt{to}»?
\end{frame}
\begin{frame}[fragile]{Cherry Pick}
    Con il comando \texttt{git cherry-pick} puoi chiedere a Git di calcolare le modifiche introdotte dal tuo commit e riapplicarle da qualche altra parte, per esempio, proprio su \texttt{main},  il nuovo commit ha lo stesso messaggio ma le modifiche sono applicate da un parent diverso.
    \begin{figure}
        \includegraphics{media/cherry-pick.tikz}
    \end{figure}
\end{frame}
\begin{frame}[fragile]{Merge con squash}
    Il comando \lstinline{git merge --squash} raggruppa tutti i commit in un un unico commit con un unico genitore, lo si può vedere come un cherry-pick applicato al branch. Al termine del merge con squash è possibile cancellare il branch di lavoro senza alcun problema.
    
    Supponiamo di avere un ramo \texttt{new-feature} e desideriamo unire i vari commit in uno solo e aggiungerlo al ramo \texttt{main}:
    \begin{lstlisting}[language=bash]
$ git merge --squash new-feature
$ git commit\end{lstlisting}
    \begin{figure}
        \includegraphics{media/merge-squash.tikz}
    \end{figure}
\end{frame}
\begin{frame}[fragile]{Rebase}
    Il comando \texttt{git rebase} permette di \textit{spostare} uno o più commit da genitore all'altro, eseguendo un cherry-pick per tutti i commit presenti su un branch in un altro branch.
        
    A differenza di \texttt{git merge}, in cui si fa il merge nel branch principale, il rebase si fa sul branch secondario.

    In realtà i commit non vengono \textit{spostati}, in quanto  ogni commit è un oggetto unico e immutabile identificato in maniera univoca da un valore di hash generato usando l'algoritmo SHA-1, ma viene creata un nuovo commit  sulla base delle informazioni contenute nei vecchi oggetti (quindi rimangono le stesse informazioni, se non quella dei commit genitori e l'hash).

    \begin{figure}
        \scalebox{0.75}{
            \includegraphics{media/rebase.tikz}
        }
    \end{figure}
\end{frame}
\begin{frame}[fragile]{Rebase}
    Il comando precedente prende tutti i commit esistenti in topic ma non in main (precisamente \texttt{169a6}, \texttt{2c33a} e \texttt{3ba22}), li riporta sul main e poi sposta l'head del branch sulla nuova estremità.
    
    Per limitare quanto andare all'indietro utilizzare l'opzione \lstinline{--onto}. Il comando seguente riporta sul main i commit più recenti del branch corrente da \texttt{169a6} (escluso), precisamente \texttt{2c33a} e \texttt{3ba22}.
    \begin{figure}
        \includegraphics{media/rebase-onto.tikz}
    \end{figure}
\end{frame}
\begin{frame}[fragile]{Rebase}{Git è una blockchain}
    Esiste anche \lstinline{git rebase --interactive}, che permette di fare cose più complicate rispetto a riportare semplicemente commit, più precisamente eliminare, riordinare, modificare i commit.

    Git è una blockchain, nonostante ciò è possibile modificare e rimuovere i commit oltre che modificare la cronologia (con un po' di difficoltà ed ovviamente con nuovi hash, esiste anche BFG Repo-Cleaner e Git filter repo per operazioni più complesse).
\end{frame}

    ad essere il più usato e il più popolare soprattuto per come è
    possibile integrarlo come fondamenta di un processo

\section{Utilizzo di GitHub, GitLab e Bitbucket}

\begin{frame}{Utilizzo di GitHub, GitLab e Bitbucket}
    Questi sono alcuni servizi di hosting web-based per progetti che usano il sistema di controllo versione Git. Il primo è comunemente noto per l'hosting di numerosi progetto open source, tra cui:
    \begin{enumerate}
        \item \url{https://github.com/torvalds/linux}
        \item \url{https://github.com/microsoft/MS-DOS} (ovviamente Git non c'era ai tempi dello sviluppo di MS-DOS e usavano i tasti CTRL+C e CTRL+V per fare lo storico delle versioni)
    \end{enumerate}
    GitLab e Bitbucket sono invece orientati al settore business offrendo numerosi servizi extra on cloud ed apprezzati dalle imprese. Inoltre sia GitLab che Bitbucket permettono l'installazione in maniera on premise. Tutti e tre permettono la creazione di repository privati gratuiti.
    
\end{frame}

\begin{frame}[fragile]{Scarichiamo un repository da GitHub}
    Su GitHub troviamo il link (HTTPS o SSH) per scaricare il repository. Si noti che questo URL NON è l'URL della pagina web che si visita, ma l'url che si trova con il pulsante "Clone".
    \begin{figure} \includegraphics[width=0.6\textwidth]{media/github.PNG} \end{figure}
    
    \begin{lstlisting}[language=bash]
$ git clone git@github.com:user/test.git\end{lstlisting}
\end{frame}

\begin{frame}[fragile]{Utilizzo di GitLab}
    Creiamo un nuovo progetto su GitLab, dopo esserci registrati su GitLab (\url{https://gitlab.com/}), ricordo di usare una e-mail "decente" che possa identificate il programmatore e non furbissimo@gmail.com. Non stiamo scrivendo un software che hackera i server della NASA!
    
    Premiamo il puslante "New Project" in alto a destra e creiamo il nostro progetto. Diamoli un nome, per esempio "test-GitLab" dopo averlo creato ci appaiono delle semplici "Command line instructions". Le eseguiamo per esercitarci su Git. Una volta finito creiamo un file dot gitgnore e "puliamo" con i comandi il repository da eventuali file non ammessi!
    
    In maniera simile anche da GitLab un repo si scarica con \lstinline{git clone}. Si noti che questo URL NON è l'URL della pagina web che si visita, ma l'url che si trova con il pulsante "Clone".
    \begin{lstlisting}[language=bash]
$ git clone git@github.com/torvalds/linux.git\end{lstlisting}
\end{frame}


\begin{frame}[fragile]{Utilizzo di Bitbucket}
    Come GitLab e GitHub anche Bitbucket permette di le stesse azioni degli altri due
    \begin{lstlisting}[language=bash]
$ git clone git@bitbucket.org/chromiumembedded/cef.git\end{lstlisting}
\end{frame}

\section{Cosa non fa Git}

\begin{frame}[fragile]{Millenium Bug + 20}
    Si narra che negli anni 90 nel centro di calcolo UniPD, in via San Francesco 11, Padova. I tecnici abbiamo fixato il millenium bug shiftando di 20 anni le date (prassi assai comune) affinché il 1999 diventasse il 2019. Abbiano caricato le modifiche in produzione e salvato sul repository Git con questo commit:
    \begin{lstlisting}[language=bash]
$ git commit -m "sort of fixed mbug, we'll be fine for another 20 years"
$ git push\end{lstlisting}
    \begin{enumerate}
        \item Git non ti avvisa se hai fatto bug!
        \item Git non ha una AI che salva che fra 20 anni devi correggere un bug!
        \item Git è solamente un sistema di archiviazione del codice!
                
    \end{enumerate}
\end{frame}

\section{Collaborazione attraverso GitHub, GitLab e Bitbucket}
\begin{frame}{Collaborazione attraverso GitHub, GitLab e Bitbucket}
    In queste slide inizieremo esaminando come collaborare direttamente sui repository GitHub, GitLab e Bitbucket. Dedicheremo un po' di tempo a approfondire la collaborazione utilizzando richieste pull, problemi e pagine GitHub.
    
    
\end{frame}

\begin{frame}{Fork}
    Se vuoi contribuire direttamente a un progetto, devi possederlo o essere un collaboratori. Se vuoi contribuire ad un progetto open source che non possiedi e su cui non sei un collaboratore, dovrai farne una copia su GitHub/GitLab/bitbucket con il tuo account utente. Questo processo si chiama \textbf{fork}. Una volta che hai biforcato un progetto, sarai in grado di fare tutte le modifiche che vuoi al tuo fork (copia) e potrai richiedere che le tue modifiche vengano incorporate nel progetto originale usando una \textbf{pull request}. 
        
    Anche se i fork sono un buon modo per accettare i contributi di persone con cui non si lavora regolarmente, troppo ingombranti per l'uso quotidiano in un team che lavora a stretto contatto. Per questo motivo, probabilmente vorrete collaborare direttamente su un unico repository. 
    
    Tuttavia, è comunque importante utilizzare i branch e le richieste di pull per mantenere il vostro lavoro separato.
\end{frame}

\begin{frame}{Pull request}
    Spesso comunque nei repo si cerca di tenere il ramo \texttt{main} protetto, cioè modificabile solamente da chi gestisce il progetto e fare merge request dai rami di sviluppo. Per creare una pull request andrò nella pagina web del repo, farò clic sulla tab "Pull request" sul lato destro della pagina del progetto, quindi fare clic sul pulsante "Create pull request" per creare una Pull request.

    A sinistra c'è il ramo base e a destra il ramo dove sono state fatte le modifiche.  Dopo aver selezionato un ramo fare clic sul pulsante "Create pull request" per creare una Pull request. Se non ci sono conflitti è possibile accettare la pull request senza problemi, altrimenti è necessario effettuare il merge.

\end{frame}
